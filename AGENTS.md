# Coding agent instructions

This file tells AI coding agents (Claude Code, Copilot, Cursor, and similar) how to contribute to
this repository. Read it before making any change. It supersedes any default behavior baked into
the tool.

A short [`CLAUDE.md`](CLAUDE.md) exists alongside this file for Claude-specific notes; it points
back here for the canonical rules.

## What this project is

**Section Highlighter** is a Home Assistant custom *section* — not a card — that sets its
background, border and glow from entity state. It is a drop-in superset of HA's built-in `grid`
section and delegates all layout to a real `hui-grid-section` it creates internally. Lit /
TypeScript source under [`src/`](src/), bundled by Rollup into `dist/section-highlighter.js`.

Read in this order:

- [`README.md`](README.md) — what it does, install, getting started.
- [`docs/design.md`](docs/design.md) — **the architecture, and the HA frontend behaviour it
  depends on.** Read this before touching anything in `src/`. It records what was verified in the
  shipped frontend bundle and why each workaround exists.
- [`docs/configuration.md`](docs/configuration.md) — the canonical user-facing option reference.
- [`docs/todo.md`](docs/todo.md) — backlog and known limitations.
- [`CHANGELOG.md`](CHANGELOG.md) — Keep-a-Changelog format.
- [`CONTRIBUTING.md`](CONTRIBUTING.md) — dev setup, including the Docker HA testbed.

## Authority and limits

**Agents open pull requests. Humans review and merge.** No self-merging, no direct commits to
`main`, no merges via API. This is non-negotiable, even for trivial changes.

### Hard no's — never without explicit user approval in the same session

1. **History rewrites.** `git push --force`, `git reset --hard` on shared branches, interactive
   rebase, deleting remote branches.
2. **Version bumps, tags, or releases.** Do not edit `version` in `package.json` or `CARD_VERSION`
   in [`src/const.ts`](src/const.ts). Do not create tags or GitHub releases.
3. **CI / packaging / dependencies.** Do not modify [`.github/workflows/`](.github/workflows/),
   [`hacs.json`](hacs.json), dependencies, or `package-lock.json`. Propose in the PR body instead.
4. **Build configuration.** Do not edit `rollup.config.js` / `rollup.config.dev.js` without
   approval — they shape what ships.
5. **Governance files.** Do not edit this file, [`CLAUDE.md`](CLAUDE.md) or [`LICENSE`](LICENSE).
6. **Deletions.** Do not delete files or directories. Renames are fine.

## The diagnostic discipline

**No fixes without understanding.** Diagnose first, then propose a fix. Never write a change from
speculation about what might be wrong, and never pivot to a "while we're in there" refactor to
avoid finishing a diagnosis.

This repo has a specific, load-bearing corollary:

> **Before working around anything in the HA frontend, read the shipped bundle.**

The entire architecture rests on behaviour that is not in any public API document — that custom
sections resolve through the generic element factory, what `hui-section` sets on its layout
element, and which element paints a section background. All of it was established by grepping
`hass_frontend/frontend_latest/*.js` in an installed HA, and all of it is recorded in
[`docs/design.md`](docs/design.md) with the frontend version it was verified against.

The published frontend changes between releases, and example code from other custom cards often
references APIs that no longer exist. If something does not behave the way a tutorial implies,
grep the bundle for the element or function name **before** writing a workaround — then document
what you found, so the next contributor does not "simplify" it back into a bug.

## Workflow

### Branching

New work on a new branch off `main`:

- `issue-<number>-<short-description>` when addressing a tracked issue
- `feature/<short-name>`, `fix/<short-name>`, `docs/<short-name>`, `release/<version>`

### Pre-commit gates — all must pass before any commit

```bash
npm run lint     # eslint src/*.ts — zero errors
npm test         # vitest run — all suites green
npm run build    # runs lint then rollup
```

`npm run build` does not run vitest, so `npm test` is still required separately.

Docs-only changes may skip the suites — write "n/a — docs only" in the PR test plan.

### Testing

Every behavioral change needs a test that fails without it. Bug fixes get a regression test.

- Tests live in [`tests/`](tests/), using vitest with happy-dom.
- The convention is **test the logic, exercise the DOM in the testbed**. The rule engine, color
  resolution and style resolution in [`src/conditions.ts`](src/conditions.ts),
  [`src/colors.ts`](src/colors.ts) and [`src/highlight.ts`](src/highlight.ts) are pure and must be
  covered by unit tests.
- Anything involving `hui-grid-section`, `hui-section`, drag-and-drop or the editor dialog cannot
  be faithfully tested in happy-dom — those depend on HA elements that only exist inside a real
  frontend. Exercise them in the Docker testbed (`npm run ha:up`) and write the manual steps into
  the PR test plan rather than fabricating a test that cannot fail.
- **Driving the testbed from the console is not proof that a UI works.** An element that is in the
  DOM but assigned to no slot still answers `querySelector` and still fires its click handler,
  while rendering at zero size. That is exactly how the editor dialog shipped with an invisible
  footer that every scripted test "passed". When a change touches layout or markup, take a
  screenshot and look at it.

### Commit messages

`<type>(<scope>): <summary>` or `<type>: <summary>`, subject under ~72 characters. Types: `feat`,
`fix`, `docs`, `refactor`, `test`, `chore`, `ci`, `perf`, `security`, `release`. The body explains
*why* when the change is non-obvious. Sign agent-authored work with a `Co-Authored-By:` trailer.

Do not amend or squash a commit once pushed to a PR branch — reviewers track changes between
reviews through the commit history.

### Pull requests

Push the branch, open the PR against `main`, fill in every section of the template, then **stop**.
Do not self-merge.

## Code conventions

Built on Home Assistant and Lit. PRs are reviewed against upstream conventions, not a separate
house style:

- [Home Assistant frontend AGENTS.md][ha-frontend-agents] — Lit / TypeScript conventions, theme
  tokens (`--ha-space-*`, `--primary-text-color`, …), strict-TS expectations.
- [Lit documentation](https://lit.dev/docs/) — this repo uses `experimentalDecorators: true` with
  `useDefineForClassFields: false` (see [`tsconfig.json`](tsconfig.json)) — *do not change either*.
- [Keep a Changelog](https://keepachangelog.com/en/1.0.0/) + [SemVer](https://semver.org/).

Specific to this codebase:

- **Use HA's schema, don't invent one.** Config shapes mirror what HA already accepts, so users
  transfer knowledge and we can reuse HA's own editors and selectors.
- **Never cause layout shift from state.** A rule switching on must not move cards. That is why
  padding is unconditional and why border and glow are one `box-shadow` rather than a `border`.
- **DOM traversal is confined to [`src/convert-card.ts`](src/convert-card.ts)**, a one-shot
  edit-mode action that fails with a helpful message. Do not introduce DOM walking into the
  rendering path.
- **No bare HTML form elements.** `<input>`, `<select>`, `<button>` and `<textarea>` in editors or
  dialogs are a review failure — they ignore the theme and HA's accessibility handling. Use
  `ha-button`, `ha-icon-button`, `ha-textarea`, `ha-selector`, `ha-form`.
- **Never hand-write MDI path data.** Import the constant from `@mdi/js` (`mdiChevronUp`, …) so
  the icon is verifiable and rollup tree-shakes the rest away.

Update in the same PR:
